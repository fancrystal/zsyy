## 本地环境

Node.js 22.12+；pnpm 10.15.0；MySQL 8+。本机用已有 MySQL 8.4 Docker 镜像创建了独立 `zsyy-mysql` 容器，绑定 `127.0.0.1:3308`，使用 `zsyy_dev` 和独立 `zsyy_test` 数据库。其他项目库没有导入或修改。

```powershell
# 已有本地容器时可直接启动
docker start zsyy-mysql

# 新开发环境：Docker Desktop 启动后，创建项目专用环境
node scripts/setup-local.mjs
node .tools/node_modules/pnpm/bin/pnpm.cjs install --store-dir .cache/pnpm

# 初始化表与初始账号；重复执行不清空数据
node packages/backend/src/initialize.js

# 同时启动 API、用户端、管理端
node scripts/dev.mjs
```

有全局 pnpm 时可使用 `pnpm install`、`pnpm dev`、`pnpm db:init`。`.tools` 是本机安装的 pnpm，不随仓库分发；新机器应先安装对应 pnpm，或通过 npm 安装项目本地 pnpm。

- 用户端：http://localhost:3011/
- 后台：http://localhost:3011/admin/
- JSON 健康接口：http://localhost:3011/api/health
- API 仅本机监听：http://127.0.0.1:3000/

初始管理员和根用户的本机凭据保存在 `.cache/development-accounts.md`，初始化输入来自 `.env`。密码不输出到日志、不提交仓库，也不复制到服务器。根用户用于登录后分享邀请码，普通注册必须有有效邀请码。初始真实余额为 0；本地 HTTP 验收另创建了“本地联调用户”，不是正式会员数据。

跨设备数据以数据库为准，不再依赖同一个浏览器的 localStorage。用户端和后台使用各自 HttpOnly Cookie，生产通过同源 HTTPS 访问。直接访问 3013 也配置了 API 代理，但日常统一使用 3011 下的入口。

## 账务与结算

下单事务按以下顺序完成：校验幂等和钱包来源 → 商品、地址及价格校验 → 写订单快照 → 扣券和消费流水 → 更新每个祖先对应市场 → 累计差额返利及流水 → 提交。任何业务失败不能留下部分订单或扣款。

首版所有账务写入先锁定一个 MySQL 互斥行，保证树上并发写入的正确性。该选择会串行化账务写操作，暂不面向高吞吐量；不依赖 Redis 分布式锁。后续确有吞吐需求再细化锁粒度。

每日北京时间 02:00 补查，服务启动时补跑最近应执行日期。任务先按用户分批核对订单/发券/返利与流水的双向来源、余额链和已发累计，再分批重建派生市场并补发。默认每批 10 个用户，批次间释放账务锁，保存阶段、游标、累计处理数及补发数。进程中断后，60 秒租约过期可由后续进程继续相同任务；失败任务保留游标重试。

已发现的源账异常会隔离相关账户和祖先；源账存在问题时该任务不进入补发阶段。实时返利同样核对已发累计和余额来源。异常钱包拒单时保留异常记录，不因拒单事务回滚而丢失。负差额不自动扣回。

手工数据库修改应先停止账务写入，保持订单、流水和余额一致；普通编辑界面不提供改余额、删流水或换上线。

## 开发者维护命令

```powershell
# 对账、重建派生汇总并补发；指定 key 可重复执行同一个请求
node packages/backend/src/maintenance.js reconcile --key maintenance-20261025

# 人工券调整：units 是 0.01 券的整数单位；10000 表示 100 券
node packages/backend/src/maintenance.js adjust --user 2 --units 10000 --note "线下登记调整" --key unique-adjustment-001

# 修复来源数据后解除指定账户隔离
node packages/backend/src/maintenance.js resolve --user 2 --note "已核对并修复来源数据"
```

调整命令同步写钱包、manual_adjustment 流水和审计，负数调整不允许余额变负。相同调整 key、相同内容重复执行不再入账；相同 key 不同内容拒绝。

解除隔离前会核对全部来源账、重建目标市场并检查应得不低于已发。来源仍错误或存在未处理的历史负差额时拒绝解除。被标记的祖先应在源问题修复后分别核对解除；解除本身不抹掉历史流水，也不自动扣回已发返利。异常记录保留为 resolved。

## 同服务器部署准备

服务器沿用现有 Node.js、MySQL 环境即可，无需将本机开发 Docker 数据目录复制过去。创建独立数据库和数据库用户，设置生产 `.env` 以及新 JWT 密钥、初始账号，不复用 mskj 的业务库或本机密码。

建议 API 使用独立端口 `3020`，避免与 mskj 的 3000 冲突。构建后将 H5 产物复制到站点 public 目录，后台产物复制到 public/admin，保留后台 `/admin/` 资源前缀。

已提供 [Nginx location 示例](../deploy/nginx.locations.conf.example) 和 [systemd 服务示例](../deploy/zsyy-api.service.example)。Nginx 片段放在商城独立的现有 HTTPS 虚拟主机中，TLS 沿用服务器配置；不要覆盖 mskj 站点。生产 Cookie 默认 Secure，必须通过 HTTPS。

上线前应在目标服务器验证数据库备份恢复、实际域名、文件权限和反向代理；本次只准备配置，未登录或修改远程服务器，未执行发布。
