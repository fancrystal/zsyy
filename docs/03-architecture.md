# 技术方案与框架设计

## 总体结构

沿用参考项目的 Vue 3 + Express + MySQL 技术路线，重新创建精简 pnpm workspace。用户端和后台独立构建，共用同一业务 API。首版采用单体服务和关系数据库事务，不引入消息队列、微服务或独立结算服务。

```text
手机 H5 ──────┐
              ├─ HTTPS / 反向代理 ─ Express API ─ MySQL
独立管理后台 ─┘                         │
                                      ├─ 每日补查任务
                                      └─ Redis（限流、辅助任务锁）
```

各业务模块内按需要设置 route、service、repository、validation 文件，不为简单查询强行创建空抽象。返利公式是纯函数，与 HTTP、数据库分离。事务由业务服务统一持有，子模块接收同一个数据库连接，禁止嵌套提交。

## 下单事务

1. 验证会话、商品 ID、正整数数量和幂等键。
2. 开始事务，以用户和幂等键检查历史请求；同键不同请求内容返回冲突。
3. 校验商品上架状态、服务端价格、有效默认地址；冻结商品和地址快照。
4. 读取并校验祖先链，确认无环；确定购买者及全部祖先账户锁集合。
5. 按统一的用户 ID 顺序锁定所有受影响的钱包和返利状态，所有账务入口遵循同一锁顺序。
6. 使用整数算术校验价格乘数量、余额和可存储范围，生成成功订单、扣减余额和消费流水。
7. 为每个祖先增加对应直属市场累计消费，并使用最新累计值计算返利。
8. 对正差额写入返利记录、增加余额、更新返利状态并写入流水，全部在当前事务中执行。
9. 提交后返回订单和最新余额；出错则整体回滚。数据库死锁允许有限次数重试完整事务，并沿用原幂等键。

发券、补算也锁定相同的钱包与返利状态。补算按单个受益人短事务处理，不持有整棵树的长事务锁。树归属在正常业务中不可变，手工关系维护必须停写。

## 一致性及恢复

- MySQL 为订单、余额、流水、累计消费和返利记录的权威存储。
- 订单幂等键、账务业务来源和返利累计目标均使用数据库唯一约束。
- 任务使用持久化运行记录，失败留存错误和处理进度，重试继续差额补发。
- 日常补查对照成功订单重建的消费统计，发现偏差先记录并修复受控汇总；负差额不自动扣回。
- Redis 故障不能造成重复发券；核心业务正确性由 MySQL 事务和约束保证。

## 接入及权限

用户与管理员身份独立校验，密码使用 bcryptjs 哈希，认证采用 JWT。后台身份不能由普通用户修改字段获得。配置项集中管理，生产拒绝空数据库配置和默认 JWT 密钥，密钥不提交仓库。

接口使用参数化 SQL、服务端输入校验、分页上限和登录限流；日志不输出密码、令牌或完整收货地址。收货地址仅本人及授权后台可查询。公司介绍不直接渲染未经处理的 HTML。

## 版本和运行约定

参考项目使用 Node.js 20+、pnpm 10、MySQL 8+。搭建时核对实际可用版本与兼容性，再固定运行版本及依赖锁文件；本阶段不安装依赖。计划采用 Vitest 运行规则及服务测试、Supertest 验证 API，使用独立 MySQL 测试库验证真实事务和并发行为，不能用内存模拟替代账务集成验证。
