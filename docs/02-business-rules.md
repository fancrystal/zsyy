# 业务与返利规则

## 1. 产品券

产品券是站内计量单位，不建立现金兑换比例。来源为后台发放、开发者账务调整、直推收益和团队返利；用途为商城下单。余额不能为负数，不做充值、转账、提现或现金支付。

建议最小单位为 0.01 券。程序和数据库按整数最小单位计算，API 用十进制字符串展示，如 `"12.50"`。禁止用 JavaScript 浮点数直接累计账务金额；数据库大整数和 Node.js BigInt 在 API 边界转换为字符串。

后台发券、订单消费、直推收益、团队返利、开发者调整分别记录不同流水类型。每次余额变动必须有唯一业务来源、变动前后余额和时间。返利可再次用于购买，该购买属于新消费。

## 2. 邀请关系

每个用户有唯一邀请码和最多一个直接上线。普通用户必须用有效邀请码注册，上线在创建用户时绑定；根用户由开发者初始化，无上线。一个上线可拥有任意多个直属下线。不得形成环、自己邀请自己或绑定不存在的用户。

注册完成后，用户及普通后台不提供修改入口。开发者维护关系属于异常维护，应先停写并校验历史市场归属，具体见运行维护文档。

## 3. 子市场和消费

对用户 A，其每个直属下线 B 对应一个子市场，范围为 B 本人及 B 的全部后代。不同直属下线的市场不重叠。A 自己的消费不计入 A 的子市场，但计入 A 的各级祖先所对应的子市场。

只统计成功扣券的订单实际消耗量。发券、券余额、注册人数、返利到账都不是消费。每笔订单对每个祖先只累计一次，不设参与返利的层数上限。每个祖先独立判断最大市场和应得返利。

首版订单不可取消或退款，因此正常业务中的各市场累计消费只能增加。商品和地址的后续修改不改变订单及累计消费。

## 4. 直推收益与累计返利

成功订单仅在规则上线后产生直推收益：购买人的直接上级即时获得 `floor(订单实际消耗 × 20 / 100)` 最小券单位产品券。该收益只发给直接上级，不向更高祖先重复发放；根用户自己的订单不产生直推收益。每笔订单最多一条直推收益记录及对应钱包流水，订单幂等重放和每日补查不得重复发放。若直接上级已因账务异常被隔离，则沿用隔离规则暂停自动入账。

直推收益与以下 10% 团队累计返利并存；直推收益不计入市场消费，也不计入团队返利的已发累计。

设用户各直属子市场累计消费为 `M1 ... Mn`：

```text
总市场消费 S = sum(M1 ... Mn)
最大市场消费 L = max(M1 ... Mn)，没有市场时为 0
累计计奖消费 E = S - L
累计应得返利 R = floor(E × 10 / 100)    # 以最小券单位计算
已发放返利 P = 历史成功返利入账累计
本次补发 D = R - P
```

- `D > 0`：增加余额、记录返利及流水、更新已发放累计。
- `D = 0`：无需入账。
- `D < 0`：属于手工数据回调或数据异常，记录异常，不自动扣券；该用户暂停自动补发，核对修复后恢复。

没有子市场或仅一个子市场时，累计应得均为 0。最大市场并列时只排除其中一个，另一个仍参与计奖；为稳定展示，按直属下线 ID 升序选择一个最大市场。

最大市场随累计消费动态变化，不永久锁定。按累计总额计算后再舍入，不能将每笔订单返利分别舍入后累加，否则小额消费会永久丢失精度。

## 5. 示例

| 场景 | 市场累计消费（券） | 累计应得（券） | 已发（券） | 本次补发（券） |
| --- | --- | --- | --- | --- |
| 三个市场 | 10000、6000、4000 | 1000 | 800 | 200 |
| 原最大市场继续增长 | 12000、6000、4000 | 1000 | 1000 | 0 |
| 另一市场成为最大 | 12000、15000、4000 | 1600 | 1000 | 600 |
| 两个最大市场并列 | 100、100、20 | 12 | 0 | 12 |
| 只有一个市场 | 100 | 0 | 0 | 0 |

正常消费单调增加时，`S - L` 不会下降，最大市场切换不应导致历史返利被扣回。

## 6. 触发与补查

下单成功时，对购买者全部祖先的对应市场累计消费进行更新，随后重算这些祖先的累计应得。首版建议在同一数据库事务内完成消费和返利入账，事务失败时整体回滚，避免订单成功但消费或返利缺失。

每天固定时间再执行全量补查。建议北京时间 02:00，具体时间可配置。补查按数据库持久化进度分批执行，可重试、可中断恢复；启动时检查漏跑日期。数据库事务和唯一约束是防重依据，定时任务锁只是辅助。

每日补查需要先检查消费来源及市场汇总的一致性，再补发正差额。不能只读取可能已经失真的缓存，也不能每天重新发放完整累计应得。

## 7. 开发者手工修改的边界

系统无法从任意 SQL 自动判断业务意图。仅修改余额不会生成消费；仅修改市场汇总会在对账时被识别为偏差。消费补录必须有订单依据、地址和商品快照、扣券流水及相应汇总更新，优先使用后续提供的维护命令。

直接修改上线、减少历史消费或删除已返利数据可能产生无法自动修复的负差额，需按维护流程处理。每日补查不是任意数据库修改的自动修复器。
