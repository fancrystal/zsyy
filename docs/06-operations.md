# 运行、对账及数据库维护

## 环境与部署方案

生产通过 HTTPS 提供手机端、独立后台和 API，反向代理将 `/api` 转发给 Express。管理员后台可使用独立域名或独立站点路径。MySQL 持久化保存全部业务账目，Redis 作为辅助组件。首次部署先执行迁移，再由开发者初始化根用户和管理员。

计划配置项：`NODE_ENV`、`PORT`、`DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`JWT_USER_SECRET`、`JWT_ADMIN_SECRET`、`REDIS_URL`、`APP_TIMEZONE`、`RECONCILE_CRON`、`PUBLIC_APP_URL`、`CORS_ORIGINS`。默认业务时区 `Asia/Shanghai`，建议补查表达式 `0 2 * * *`，调度器显式设置业务时区。

后续提供 `.env.example`，仅包含占位值。实际密钥、生产地址和数据库备份不提交仓库。本文配置名为设计约定，实施时须与启动校验一致。

## 每日任务

1. 取得辅助执行锁并创建或恢复当天 job_runs。
2. 分批核对成功订单及对应消费流水，发现源账不一致时记录异常并隔离受影响范围，不凭空创建扣款。
3. 对源账一致的订单按当前有效关系计算预期市场累计消费，核对派生汇总。修复时与下单采用相同锁和事务约定，读取一致快照，避免覆盖并发新消费。
4. 对每个无未解决源账异常的受益人锁定状态，核对已发累计并计算差额；正差额入账，负差额标记异常，零差额跳过。
5. 成功提交后更新进度，记录扫描数、补发金额、异常数及结束时间。

任务失败保留进度，重试仍依靠同一账务防重逻辑。服务重启时检查漏跑任务，补查至当前业务日期，不按漏跑天数重复发放累计金额。大批量历史重建在维护窗口停写执行，在线补查首版可逐账户短事务核对，避免长时间占锁。

## 直接修改数据库

允许开发者维护数据，但不同修改需要不同配套操作：

| 修改 | 配套要求 |
| --- | --- |
| 发券或余额调整 | 同一事务更新钱包并新增 manual_adjustment 流水，记录原因和维护者 |
| 商品和公司信息 | 校验字段，保留已有订单快照 |
| 新建用户 | 密码哈希、唯一邀请码、有效父节点、零余额钱包、返利账户及直属市场记录一起创建 |
| 补录真实消费 | 完整订单、扣款流水及余额必须一致，再更新或重建市场汇总、补算差额 |
| 改上线 | 停止下单和结算，验证无环，审查历史消费归属，重建受影响市场并检查返利差异 |
| 减少消费或改历史数据 | 维护窗口审查已发返利，负差额转人工处理，不自动扣回 |

不能只改 wallets.balance_units 后期待流水自动生成，不能只改市场汇总后期待该值永久成为真实消费。系统也不会将单纯余额增加视为消费。

### 建议维护流程

1. 备份并记录要变更的用户及原值。
2. 按变更范围暂停下单、发券和结算，或锁定受影响账户。
3. 在事务内完成全部关联更新并记录维护日志。
4. 对账钱包与流水、订单与消费、市场与关系、已发与返利明细。
5. 对可补发正差额执行幂等补算；负差额和来源异常先人工核对。
6. 验证页面显示和订单记录后恢复写入，保存维护结果。

已有消费的关系变更会改变历史市场归属，不能视为普通资料修改。首版默认历史订单按当前不可变关系归属；不开发自动迁移历史返利的功能。

## 对账检查

- 钱包余额是否等于全部流水净额，是否出现负余额。
- 订单金额是否等于商品快照单价乘数量，对应消费流水是否唯一且金额相反。
- 市场累计是否与订单和关系重建结果一致。
- 已发累计是否等于返利明细，返利明细是否都有唯一流水。
- 是否出现环、缺失父用户、缺失钱包、缺失地址快照。
- 是否存在累计应得小于已发或任务持续失败。

## 备份及恢复

迁移前及维护前备份数据库；上线后按业务量设置定期备份，并至少验证一次从备份恢复到独立数据库。钱包、流水、订单、关系、返利必须作为同一一致性集合恢复，不能只恢复余额表。恢复后先停写对账，再运行补查，确认无重复入账后开放访问。

## 日志及排障

日志记录 requestId、订单 ID、任务 ID、耗时及错误类型，不记录密码、完整令牌或完整地址。HTTP 返回成功必须晚于事务提交。遇到提交后响应丢失，客户端用原幂等键查询或重试，不能新建重复消费。
